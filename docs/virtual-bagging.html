Virtual Bagging

Build the BagIt bag inside the tar stream instead of restructuring the research drive in place.

Estimated effort: 3.5–5 dev-days (about a week with review). No API, database, or retrieval-side changes.

Why change

The problem with bag-in-place

Today an archive submission mutates the source drive: bagit.make_bag() moves every file into a data/ directory, checksums the lot, and writes bag metadata at the drive root. The rename-based restructure is nearly free, which is why we chose it over copying — but make_bag is not crash-safe and not idempotent, and our “is this already a bag?” check can’t tell never bagged from half bagged.

Reading the installed bagit source confirms the ordering: restructure first, then the hours-long checksum pass, and only then bagit.txt — the very file our check looks for. So a crash in either of the first two phases leaves a state where retrying silently re-wraps the debris: the archive ends up with a stray temp directory or a double-nested data/data/… layout, and the job reports success. A further cost of the current design: every byte is read twice — once to checksum, once to tar.

Proposed design

Synthesize the bag in the archive only

We already build the tar ourselves and stream it into chunked parts. Instead of tarring a restructured drive, we walk the untouched source, write each file into the tar under data/, compute its SHA-256 while the bytes stream through, and append the generated BagIt tag files as tar entries at the end. The extracted archive is a fully valid BagIt bag; the source drive is never written to at all.

The RO-Crate metadata file is generated into local scratch (it is a single JSON file) and injected into the tar as payload, with its hash in the manifest — exactly where the profile expects it.

What this buys us

  • The crash-inconsistency class is deleted, not managed. A failed or interrupted job leaves the source drive byte-identical to before. Retry is trivially safe — no repair logic, no sentinel states.
  • One read pass instead of two. Checksums are computed from the same bytes being tarred. On SMB, where reads dominate wall-time, this roughly halves archive runtime.
  • Integrity by construction. Today the checksum pass and the tar pass read at different times; any change to the drive in between (admin tooling, sync agents) yields a manifest that doesn’t match the archived bytes, undetected until retrieval. Streaming hashes exactly the bytes that enter the archive, so the manifest is guaranteed to match — independent of the pre-job access freeze.
  • Read-only source. The write-probe on the drive goes away; drives can be mounted read-only — consistent with researcher access being removed before a job runs, a better isolation posture, and a good fit for the planned split-worker architecture.
  • The frozen drive stays frozen. Access is removed before a job precisely so the drive is a fixed snapshot — bag-in-place then immediately restructures that snapshot. Virtual bagging keeps the handed-over state byte-identical, which also keeps verification simple for the future delete-after-archive workflow.
  • Sidesteps the Linux constraint that currently forces single-process checksumming (PROCESSES = 1) — hashing rides the I/O-bound streaming pass.

What it costs

  • Bag creation moves from the bagit library into ~250 lines of our own code (manifest, bagit.txt, bag-info.txt with Payload-Oxum, tagmanifest — simple, well-specified formats). The bagit library remains the validation oracle, both in tests and at retrieval.
  • Filename edge cases (BagIt percent-encoding of CR/LF/%, unicode on SMB) are ours to handle — mitigated by round-trip tests that extract and validate with bagit itself.
  • Empty directories survive in the tar but aren’t protected by BagIt manifests — identical to today.

Scope of change

What changes, component by component

ComponentChange
packaging/bag_stream.py newDeterministic walk of the source; per-file tee-hashing into the tar via tarfile.addfile; synthesis of the four tag files as in-memory tar entries. ~250 lines.
packaging/archive_chunks.pyContent of the tar comes from the bag streamer instead of one tar.add(drive) call. The split-part writer, chunk manifest, and reassembly logic are below the tar layer and don’t change.
workers/submission_worker.pybuild_crate_contents simplifies: crate JSON to scratch; the bag_directory call and the bagged/unbagged branching are deleted.
utils/paths.pyDrop the write-probe on the source drive (keep read-probe and temp-space probe). Source can be read-only.
packaging/manifests.pyPrune the creation path (bag_directory, create_manifests_directory — the latter currently builds an artifact that is always deleted unused). Keep bagit_exists / validate_bag for retrieval.
Retrieval workerUnchanged — the extracted tar is a valid bag and already gets validated.
API, DB schema, S3 layoutUnchanged. Chunk-part naming, archive manifest, retention, and resume-invalidation logic all stay as-is.
Transition caveat: drives already bagged in place by earlier runs contain a real data/ + bagit.txt. Wrapping them again would double-nest. Either keep a thin legacy branch (“if already a bag, tar as-is”) or manually un-bag the handful of test drives. Pre-production, both are cheap.

For the team

Decisions needed

1. Approve the direction?
Virtual bagging vs. hardening bag-in-place (crash-state detection and repair, ~2–3 days, keeps both read passes and the in-place mutation). Recommended: virtual bagging — it removes the failure class instead of managing it, and the effort is comparable.
2. Legacy bagged drives
Thin compatibility branch, or manually un-bag existing test drives? Recommended: manual un-bag if only test drives are affected — keeps the code single-path.
3. In-stream verification
Include the optional hash-verification pass in scope? Recommended: yes — cheapest point we will ever be able to add it.
4. Bag remnant on the drive
The future deletion workflow wants a manifest copy left on the drive. Under virtual bagging that becomes one explicit small file write at a time of our choosing — confirm it belongs to the deletion workflow, not archiving.
